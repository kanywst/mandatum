## 1. 問題

人間の代わりに行為する AI エージェントは、今日ほぼ例外なく**クレデンシャルを継承する**ことでそれを行っています。サービスアカウント、API キー、共有 OAuth トークン、あるいは人間自身のセッション。ここから3つの失敗が直接導かれ、そのいずれも仮定ではなく実測されたものです。

1. **帰属がない。** エージェントの行動を全環境で人間のスポンサーまで追跡できる組織は 28% に過ぎず、68% はエージェントの活動と人間の活動を確実に区別できません（Cloud Security Alliance, *State of NHI and AI Security*, 2026年1月）。
2. **選択的な失効ができない。** エージェントは継承したクレデンシャルを共有しているため、1つのエージェントを失効させると、そのクレデンシャルを使うすべてのプリンシパルが巻き添えになります。これが *credential piggybacking* と呼ばれる失敗モードです。
3. **並びに対する制御がない。** 認可は呼び出しごとに評価されます。エージェントは一連のリクエストの各々について個別に認可されていながら、その*一連*が誰も認可していない結果を生むことがあります。現行のプロトコルは行動の並びに対する制約を表現できず、単一の行動に対する制約しか表現できません。

Model Context Protocol の認可層は、自らのスコープの限界を明示しています。認可はトランスポート層で定義されるものであり、ツール単位の認可、エージェント識別、委任、同意はスコープ外である、と。Enterprise-Managed Authorization 拡張（stable, 2026-06-18）も自身の言葉で同じことを述べています。それが統べるのは接続であって、個々のツール呼び出しではありません。

Mandatum はまさにこの隙間だけを扱います。

## 2. 非目標

先にこれを述べるのは、この領域のプロジェクトの失敗モードが、既に占有された領域へのスコープクリープだからです。

- **新しい認可エンジンではない。** Mandatum は判定を一切しません。判定に必要な事実を運び、既に存在する Policy Decision Point（OPA、Cedar、OpenFGA、SpiceDB、Cerbos、あるいは AuthZEN 準拠の任意の PDP）を呼びます。
- **新しいワイヤプロトコルではない。** 委任は JOSE で表現し、RFC 8693 のトークン交換で発行し、OpenID AuthZEN Authorization API 1.0 で評価します。既存標準が適合する箇所では、Mandatum はそれを変更せずに使います。
- **ゲートウェイではない。** Mandatum はライブラリとミドルウェアとして提供されます。agentgateway、ToolHive、MCP サーバ、エージェントランタイムの*内側*で動くことを意図しており、それらを置き換えるものではありません。
- **レジストリ・サンドボックス・エージェントランタイムではない。** これらのカテゴリは占有されています。
- **ブロックチェーンではない。** 監査ログは RFC 6962 形式の Merkle ツリーです。合意プロトコルもネットワークもトークンもありません。

## 3. 先行研究

Mandatum の減衰モデルは新規ではなく、新規だとも主張しません。オフライン検証を伴うケーパビリティ減衰は macaroons（Birgisson et al., 2014）の、そして現代的な形では Biscuit の貢献です。SPIFFE は暗号学的なワークロード識別を確立しました。RFC 8693 は委任セマンティクス（`actor_token`、`act` クレーム）を伴うトークン交換を確立しました。RFC 6962 は改竄検知可能なログを確立しました。

Mandatum がこの蓄積に加えるものは狭く、具体的です。

- **認証済みの人間のスポンサーを根とする**連鎖。根はすべての葉まで変更されずに運ばれるため、任意の再委任を経ても帰属が生き残ります。
- 呼び出し単位ではなく連鎖の行動履歴全体に対して評価される、**並びスコープの制約**。
- **AuthZEN Authorization API へのバインディング**。これにより、検証済みの連鎖は特定ベンダーのエンジンではなく任意の準拠 PDP への入力になります。

既存プロジェクトがこの3つを既に実現しているとレビュアーが判断するなら、それはこのプロジェクトではなくそちらに貢献すべき理由です。[`../alternatives.md`](../alternatives.md) を参照してください。

## 4. 用語

| 用語 | 意味 |
| --- | --- |
| Sponsor | 連鎖の根にいる、認証済みの人間のプリンシパル |
| Agent | 委任されたケーパビリティ集合を持つ非人間プリンシパル |
| MDA | Mandatum Delegation Assertion。連鎖における署名済みの1リンク |
| Chain | スポンサーから行為するエージェントまでの、順序付けられた MDA の列 |
| Leaf | 連鎖の最後の MDA。行動を実行するエージェントを識別する |
| PEP | Policy Enforcement Point。連鎖を検証し PDP を呼ぶ |
| PDP | Policy Decision Point。AuthZEN 準拠の認可サービス |
| Attenuation | 親から子へのケーパビリティ集合の狭まり（減衰） |

## 5. Delegation Assertion のフォーマット

MDA は compact serialization（RFC 7515）の JWS であり、そのペイロードは JWT クレーム集合（RFC 7519）です。登録済みクレームは通常の意味を保ちます。Mandatum 固有のクレームはすべて単一の `mdt` クレームの下に置き、衝突を避けます。

```json
{
  "iss": "spiffe://example.org/ns/agents/planner",
  "sub": "spiffe://example.org/ns/agents/retriever",
  "aud": "https://mcp.example.org",
  "iat": 1789200000,
  "exp": 1789203600,
  "jti": "01JB2X9K7P4Q8R3N6M0V5T2Y7C",
  "mdt": {
    "v": 1,
    "root": {
      "iss": "https://idp.example.org",
      "sub": "u-8f31c02e",
      "amr": ["pwd", "hwk"],
      "auth_time": 1789199400
    },
    "parent": "sha-256:UNhY4JhezH9gQYqvDMWrWH9CwlcKiECVqejMrND2VFw",
    "depth": 1,
    "max_depth": 2,
    "cap": [
      {
        "resource": { "type": "mcp_tool", "id": "search.query" },
        "action": { "name": "invoke" },
        "conditions": { "args.index": { "in": ["public", "docs"] } }
      }
    ],
    "seq": {
      "max_invocations": 200,
      "constraints": [
        { "id": "no-write-after-external-read",
          "forbid": { "action": "invoke", "resource.type": "mcp_tool",
                      "resource.tags": ["mutating"] },
          "after": { "resource.tags": ["external-content"] } }
      ]
    }
  }
}
```

### 5.1 ダイジェストの符号化

本仕様に現れるダイジェストはすべて `sha-256:<value>` の形式で表記します。`<value>` は SHA-256 の生の32バイト出力を **パディングなしの base64url** で符号化したものであり、RFC 7515 §2 の `BASE64URL` に従います。これは JOSE が既に使っている符号化なので、JWS を扱う実装なら手元にあります。

これを明記するのは些末なこだわりではありません。`mdt.parent` は連鎖のすげ替えを検知可能にするコミットメントであり、同じハッシュを異なる方法で符号化する2つの実装は、互いの生成した連鎖をすべて拒否します。

実装者が自分のエンコーダを散文ではなく本文書と照合できるよう、テストベクタを示します。

| 入力 | ダイジェスト |
| --- | --- |
| `the empty string` | `sha-256:47DEQpj8HBSa-_TImW-5JCeuQeRkm5NMpJWZG3hSuFU` |
| `example` | `sha-256:UNhY4JhezH9gQYqvDMWrWH9CwlcKiECVqejMrND2VFw` |
| `mandatum` | `sha-256:jUMrViVq7f3wcuQ44n0wJz5BNoNwIcxeu0MS7PGfEZI` |

本文書の例に現れるダイジェストはすべて、この方法で計算した実際の値であり、プレースホルダではありません。

検証者は `sha-256:` 接頭辞を確認した上で、ダイジェストを**文字列として厳密一致で比較しなければなりません**（MUST）。比較前にデコードして再符号化してはならず（MUST NOT）、同じハッシュの別の符号化を受理してもなりません（MUST NOT）。1つの値に複数の綴りを許すことは、本節が取り除こうとしている曖昧さを再導入することです。

定義されているのは `sha-256` のみです。検証者はそれ以外の接頭辞を、試みることなく拒否しなければなりません（MUST）。将来のアルゴリズムは、古い検証者が黙って受け入れるものではなく、意図的なバージョン更新であるべきだからです。

### 5.2 クレームの意味

| クレーム | 必須 | 意味 |
| --- | --- | --- |
| `iss` | yes | 委任元。depth 0 ではスポンサーの発行機関 |
| `sub` | yes | 委任先。SPIFFE ID などの安定したエージェント識別子 |
| `exp` | yes | 有効期限。親の `exp` を超えてはならない |
| `jti` | yes | 一意な識別子。失効の単位 |
| `mdt.v` | yes | フォーマットのバージョン。本文書では `1` |
| `mdt.root` | yes | 人間のスポンサー。連鎖のすべてのリンクでバイト単位で同一 |
| `mdt.parent` | yes | 親 MDA のハッシュ。depth 0 では `null` |
| `mdt.depth` | yes | このリンクの 0 始まりのインデックス。連鎖の順序を示すだけで、長さを制限するものではない |
| `mdt.max_depth` | yes | このアサーションより下で許される再委任の回数。0 は「行為はできるが再委任はできない」を意味する。1ホップごとに最低1減るため、スポンサーの値が連鎖全体を制限する。負の値は不可 |
| `mdt.cap` | yes | ケーパビリティ集合。空でもよく、その場合は権限なしを意味する |
| `mdt.seq` | no | 並びスコープの制約。省略時は並びの制限なし |

### 5.3 なぜ depth と max_depth は分かれているのか

`depth` はリンクの位置を、`max_depth` は委任があとどれだけ進めるかを表します。両者を結びつけること、たとえば `max_depth` が `depth` を上回ることを要求するのは、一見きれいですが誤りです。§6 の1ホップごとの減衰と組み合わせると**使える予算が半分になります**。位置が上がるにつれて上限が下がり、両者が中間でぶつかるためです。

独立に保つことで、スポンサーが `max_depth` に *n* と書けば再委任がちょうど *n* 回できます。その数字を書いた運用者が期待するのはそれです。

### 5.4 なぜスポンサーは参照ではなく複製されるのか

`mdt.root` は連鎖を辿って解決するのではなく、すべてのリンクに複製されます。これにより、部分的な連鎖しか受け取っていない検証者や、完全な検証を経ずにスポンサー単位で監査記録を索引したい実装でも、行動の帰属が可能になります。複製は検証時に一致が確認される（規則 V6）ため、帰属の偽造には使えません。

## 6. 減衰規則

すべてのリンク *i* > 0 について、以下がすべて成り立たなければなりません（MUST）。これらが揃うことで、連鎖は単調に広がらないものになります。

1. `cap(i)` ⊆ `cap(i-1)` — 子のすべてのケーパビリティが、親のいずれかのケーパビリティに含意される。含意の定義は §6.1
2. `exp(i)` ≤ `exp(i-1)`
3. `max_depth(i)` ≤ `max_depth(i-1) − 1` かつ `max_depth(i)` ≥ 0。この2つで予算は狭義に減少し有限になり、それが連鎖長を制限する
4. `depth(i)` = `depth(i-1) + 1`
5. `seq(i)` は `seq(i-1)` と同等以上に厳しい。数値予算は増加せず、制約集合は上位集合である
6. `root(i)` は `root(i-1)` とバイト単位で同一

いずれかの規則に違反する子は、有効な委任ではありません。このフォーマットには「承認を伴う昇格」の経路は存在せず、権限を上げるにはスポンサーから新しい連鎖を発行する必要があります。

### 6.1 ケーパビリティの含意

ケーパビリティ `c` が親ケーパビリティ `p` に含意されるのは、`c` のリソースパターンが `p` の部分集合であり、`c` のアクション集合が `p` の部分集合であり、`c` の条件が `p` と同等以上に厳しい場合です。条件の比較は決定可能な断片に限定されます。集合の所属、文字列の等価、前方一致、数値範囲の4つです。この断片の外にある条件は、検証時に近似するのではなく発行時に拒否されるため、含意が不完全なチェックによって判断されることはありません。

これは意図的な制限です。決定不能な条件言語を許すと、発行者が有効だと信じた入力に対して、検証者は fail open か fail closed のどちらかを選ばされることになります。

境界事例が2つあります。明記しないと実装が推測することになるためです。

- 空リストの `in` 条件は何にもマッチしません。したがって表現可能な中で最も狭い制限であり、任意の親条件がこれを含意します。そのケーパビリティは決して適用されず、無用ではありますが危険ではありません。拒否すると、委任元があるキーについて「何も与えない」と明示的に表明できなくなります。
- 比較を1つも設定していない条件、および2つ以上設定した条件は無効であり、発行時に拒否しなければなりません（MUST）。前者は何も制限せず、後者はこの断片が意図的に定義していない結合規則を必要とします。

## 7. 連鎖の検証

入力: 順序付けられた連鎖 `[MDA₀ … MDAₙ]`、トラストバンドル、失効オラクル、現在時刻。

- **V1 構造。** `MDA₀.mdt.parent` が `null` であり `MDA₀.mdt.depth` が 0 である。すべての *i* > 0 について、`MDA(i).mdt.parent` が `MDA(i-1)` の compact serialization に対する `sha-256` と一致する。
- **V2 保持。** すべての *i* > 0 について、`MDA(i).iss` が `MDA(i-1).sub` と等しい。委任元は自分が保持する権限しか委任できない。
- **V3 署名。** すべての MDA が、その `iss` について SPIFFE トラストバンドルまたは発行者の JWKS から解決された鍵で検証される。アルゴリズムは固定の許可リストから採り、`none` と対称鍵アルゴリズムは拒否する。
- **V4 時刻。** すべてのリンクについて `iat` ≤ now < `exp`。スキューは有界。
- **V5 減衰。** §6 のすべての規則が成り立つ。
- **V6 根の一貫性。** `mdt.root` がすべてのリンクでバイト単位で同一である。
- **V7 深さ。** `n` ≤ `MDA₀.mdt.max_depth`。ここで `n` は委任ホップ数であり、リンク数より1少ない。
- **V8 失効。** 連鎖中のどの `jti` も失効集合に含まれない。
- **V9 オーディエンス。** 葉の `aud` が検証を行うリソースサーバと一致する。

検証は V3 の鍵解決と V8 を除きオフラインで完結し、その2つもキャッシュ可能です。検証者は部分的な検証で連鎖を受理してはなりません（MUST NOT）。

V7 は現在の規則集合の中では冗長です。V5 が `max_depth` を1ホップごとに最低1減らすことを強制し、§5.2 がそれを負にすることを禁じているため、V7 に違反する連鎖は既に V5 で拒否されます。将来 V5 が緩和された場合に備えた多層防御として残しています。実装は到達不能な分岐として放置せず、直接テストすべきです。

### 7.1 失効のセマンティクス

任意の `jti` を失効させると、そのリンクと**そこから派生するすべての連鎖**が無効になります。子孫は `mdt.parent` を通じてそのリンクにコミットしているためです。これが credential piggybacking への答えです。スポンサーは、兄弟の連鎖や他のプリンシパルに一切触れることなく、1つのエージェントの権限を、それが再委任したものも含めて停止できます。

失効状態はコンパクトな集合（公開された偽陽性率を持つ Bloom フィルタと、正確な照合のためのフォールバック）として配布され、PEP はローカルで V8 を評価できます。偽陽性は許可ではなく拒否になります。

## 8. AuthZEN バインディング

検証済みの連鎖は、OpenID AuthZEN Authorization API 1.0 の評価リクエストにおける subject コンテキストになります。Mandatum は API を拡張せず、その中身を埋めるだけです。

```json
{
  "subject": {
    "type": "identity",
    "id": "u-8f31c02e",
    "properties": { "iss": "https://idp.example.org" }
  },
  "action": { "name": "tools/call" },
  "resource": {
    "type": "tool",
    "id": "search.query",
    "properties": {
      "server": "https://mcp.example.org",
      "arguments": { "index": "public" }
    }
  },
  "context": {
    "agent": "spiffe://example.org/ns/agents/retriever",
    "mandatum.delegation": {
      "sponsor": {
        "iss": "https://idp.example.org",
        "sub": "u-8f31c02e",
        "amr": ["pwd", "hwk"],
        "auth_time": 1789199400
      },
      "chain": "sha-256:LPJNul-wow4m6DsqxbninhsWHlwfp0JecwQzYpOLmCQ",
      "actors": [
        "spiffe://example.org/ns/agents/planner",
        "spiffe://example.org/ns/agents/retriever"
      ],
      "depth": 1,
      "leaf": "01JB2XA4M0RN5S8Q2K7T3W1Y9D"
    }
  }
}
```

`subject` / `action` / `resource` / `context.agent` の形は、COAZ-MCP の `tools/call` 既定マッピングそのままです。この binding では `subject` が「その代理としてアクセスが要求されている主体」、`context.agent` が「実際に行為しているクライアント」であり、これはスポンサーを根とする連鎖が元から持っている区分と正確に一致します。人間が `subject` に、葉のエージェントが `context.agent` に入ります。

`context.agent` は1ホップだけを運び、連鎖を運びません。binding は上流アクターを「別途アドレス可能」とだけ述べて置き場所を未定義のまま残しているため、Mandatum は binding の名前空間に勝手な名前を作らず、ベンダー接頭辞付きのキーに置きます。このキーが存在すること自体が主張です。PEP は §7 のすべての規則を通過した連鎖からしかこれを埋めないため、PDP が `subject.id` を信頼できるのと同じ理由でこれを信頼できます。

`actors` は「誰が上流にいたか」に答えます。`chain` はそれを単なるリスト以上のものにするもので、正確なリンク列にコミットするため、他の連鎖の断片からアクター列を組み直すことができません。このコミットメントが本当に必要か、検証済みのリストで十分かは未解決です。§12 を参照。

連鎖の検証は PDP を呼ぶ**前**に行われます。PDP が受け取るのは事実の陳述（「このエージェントは、この人間を根とする有効な連鎖を保持している」）であり、その上に組織のポリシーを適用します。両者を分離することで、運用者はクレデンシャルの扱いを変えずにポリシーを変更でき、また侵害された PDP がスポンサーの与えていない権限を捏造することはできません。

OIDF の COAZ-MCP バインディング（WG Draft, 2026年6月）が MCP ツール呼び出しから AuthZEN リクエストへのマッピングを規定している範囲では、Mandatum は並行するマッピングを定義せずそれに従います。乖離は `coaz-mcp-conformance.md` に記録します。

## 9. 並びレベルの評価

ここは既存の実装が存在しない部分なので、慎重に規定します。

**並び (sequence)** とは、1つの連鎖の根の下で実行された行動の順序付き履歴です。PEP は連鎖の根ごとに追記のみの履歴と、そこから導かれる状態を保持します。

```text
  state = fold(evaluate_constraint, initial, history)
```

`mdt.seq.constraints` の各制約は履歴に対する述語であり、候補となる行動を追記した*後*にも成り立たなければなりません。追記によっていずれかの制約が偽になる場合、その行動は制約の `id` を明示した理由とともに拒否されます。

§5 の例は、呼び出し単位の認可では原理的に捉えられない致命的なパターンを符号化しています。エージェントが信頼できない外部コンテンツを読み、その後に変更を伴う行動を実行する。各ステップは個別に認可されています。その組が情報漏洩です。

2つの性質が必須であり、それが実装の形を決めます。

- **状態の有界性。** 履歴は無制限に増やせません。制約は行動の*タグ*上の有限オートマトンにコンパイルされ、連鎖ごとの状態は履歴長によらず固定サイズのベクタになります。コンパイルできない制約は発行時に拒否されます。
- **状態喪失時の fail-closed。** `mdt.seq` を宣言している連鎖について PEP が並び状態を読めない場合、拒否します。並び制約が静かに呼び出し単位のチェックへ劣化することは、制約が無いことよりも悪い結果です。運用者は保護されていると信じてしまうからです。

並び状態は連鎖の根ごとに保持され、したがって複数の PEP 間で共有されます。リファレンス実装は開発用の単一プロセスストアと本番用の複製ストアを提供し、そのインタフェースは `sequence-store.md` で定義します。

## 10. 監査証跡

すべての判定は、許可・拒否を問わず、改竄検知可能なログに1レコードを追記します。

| フィールド | 目的 |
| --- | --- |
| `root` | 人間のスポンサー。帰属クエリを可能にする |
| `chain` | 検証済み連鎖全体のダイジェスト |
| `leaf_jti` | 行為したエージェントのリンク。失効のハンドル |
| `action`, `resource` | 何が試みられたか |
| `decision` | 許可か拒否か |
| `reason` | 構造化された理由コード。拒否時は制約の `id` を含む |
| `policy_revision` | PDP のポリシーまたはバンドルのバージョン |
| `seq_index` | 連鎖の行動並びにおける位置 |
| `ts` | タイムスタンプ |

`policy_revision` が必須なのは、これがないと判定を再現できないためです。今日のポリシーで再評価することは、ログが記録しているのとは別の問いに答えることになります。既存の decision log にこのフィールドが欠けていることが、「なぜ拒否されたのか」が実務上答えられない理由です。

ログは RFC 6962 形式の Merkle ツリーです。包含証明と一貫性証明により、監査者はレコードが改変も削除もされていないことを検証できます。EU AI Act の high-risk 義務は 2026-08-02 から適用されており、不変のログと追跡可能な委任チェーンを要求します。本節はその要求を満たすために存在し、対応関係は `../compliance/eu-ai-act.md` に記録します。

## 11. 脅威モデル

ここでは要約のみを示します。完全なモデルは `../security/threat-model.md` にあります。

| 脅威 | 緩和策 |
| --- | --- |
| 委任の偽造 | V3。トラストバンドルに対する署名検証 |
| 連鎖のすげ替え (splicing) | V1 の親ハッシュコミットメント。リンクは交換不能 |
| 再委任による権限昇格 | §6 の減衰。発行時ではなく検証時に強制 |
| 失効後のリプレイ | V8。fail-closed な配布 |
| Confused deputy | V2 の保持規則と V9 のオーディエンス束縛 |
| 帰属の剥奪 | V6 の根の一貫性。`root` は削除も書き換えもできない |
| ログの改竄 | Merkle の包含証明と一貫性証明 |
| 並び状態の回避 | 状態喪失時の fail-closed。状態は PEP ではなく連鎖の根で鍵付けされる |
| PDP の侵害 | PDP は拒否はできるが、許可は連鎖のケーパビリティ集合の範囲内でしかできない。権限を広げることはできない |

最後の行は意図的な設計特性です。検証が policy 判定に先行し、かつそれを制約するため、PDP は完全には信頼されていません。

## 12. 未解決の問い

正直な一覧です。未解決であり、意見を求めています。

1. `mdt.root` は保証レベル（`acr`）を持つべきか。影響の大きい並びに対してポリシーがステップアップ認証を要求できるようにするために。
2. 有限オートマトンによる制約言語は実運用の要求に対して十分な表現力を持つか。単純な予算を超える有界カウンティングが必要ではないか。
3. Mandatum は独自の失効配布を定義すべきか、それとも既存の状態機構（OAuth Status Lists）をそのまま採用すべきか。
4. 連鎖はトラストドメインをまたぐときどう振る舞うべきか。SPIFFE のフェデレーションは鍵解決の答えを与えるが、ドメイン間のスポンサーシップについてのポリシーの答えは与えない。
5. 委任チェーンは複数スポンサーの状況、すなわち1つのエージェントが同時に2人のために行為する場合に適した形か。それとも別の構造が要るのか。
