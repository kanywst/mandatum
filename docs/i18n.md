# Translations

English is the project's working language and the normative one. Translations exist so that the project is readable by people who would otherwise skip it, not so that English becomes optional.

## The rule that matters

**Where a translation and the English text disagree, the English text is correct.**

This is not a courtesy to English speakers. `docs/spec/` is a security specification: an implementer who follows a mistranslated attenuation rule ships an authorization bypass. Every translated specification page carries that statement at the top, and an implementer in doubt should read the English.

## Layout

A translation sits beside its source with a language suffix, using the two-letter code:

```text
README.md              ← English, normative
README.ja.md           ← 日本語
docs/spec/delegation-assertion.md
docs/spec/delegation-assertion.ja.md
```

Siblings rather than a parallel `docs/ja/` tree, so that relative links inside a document work the same in both, and so a missing translation is obvious rather than being a broken directory.

A file gets a language switcher at the top only once the other language actually exists. A switcher pointing at a file nobody has written is worse than no switcher.

## Keeping translations honest

A stale translation is more dangerous than a missing one, because a reader cannot tell.

Each translated page ends with a marker recording a **digest of its English source at the time of translation**:

```text
*translated-from: sha-256:1c370b1e…*
```

A digest rather than a commit hash, because a commit cannot name itself. When an English change and its translation land together, a commit-hash marker can only point at the commit *before* them, which reads as "this section is untranslated" when it is not. A content digest has no such problem, and it can be checked mechanically:

```bash
make translations-check   # report translations whose source has moved on
make translations         # re-stamp them as current, after actually translating
```

CI runs the check on every pull request that touches a Markdown file, and on every push to `main`. It is advisory and does not block: an English correction must not wait for a translator, and a maintainer who does not speak the language should still be able to fix a typo. `make translations` only moves the marker — run it after bringing the text across, not instead of.

If you find a translation that has drifted, opening an issue is useful even if you cannot fix it.

## Adding a language

1. Copy the English file to `<name>.<lang>.md`.
2. Translate it. Keep code, identifiers, claim names, RFC numbers, and rule identifiers (`V1`, `mdt.v`) untranslated — they are the interoperable part.
3. Add the header block with the normative-English notice, and a `translated-from` marker at the foot. Any 64-hex digest works as a placeholder; `make translations` will stamp the real one.
4. Add switcher links to every language variant of that document, including the English one.
5. Add a row to the table above.

You do not need to translate everything to contribute a translation. One well-translated document is worth more than five half-translated ones.

## What not to translate

- Identifiers, claim names, JSON keys, rule identifiers.
- `CHANGELOG.md` — it is a release record that must have exactly one authoritative version.
- `LICENSE` and `NOTICE` — legally operative text.
- `security-insights.yml` — machine-read.
